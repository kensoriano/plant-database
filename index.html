Try it: press Save on any plant card and choose the firm master list or a project. In this preview, saves are kept only in your own browser. In the real database they'd be shared by the whole firm.

What you're looking at

Every plant is one row in the database. The search page just reads those rows and shows them as cards. Change a value in the database and the page updates, with nothing to retype in a layout.

The tables, in plain English

The database is a set of tables, like tabs in an Excel workbook, that point to each other:

plantThe main list. One row per plant: names, height, spread, zones, bloom months, bloom color, yes/no flags.
Like your "Database" sheet.
Lookup tablesThe allowed choices: plant types, sun levels, soil moisture levels, soil conditions, foliage types, seasons, landscape uses, wildlife.
Like the dropdown lists behind a data-entry form. They stop "Full Sun" from also being typed "full sun" or "FS".
Link tablesConnect a plant to several choices at once. "Part Shade" and "Full Sun" can both belong to one plant.
This replaces cramming "clay, loam, sand" into one cell.
plant_image + image_typePhoto file names, plus what each photo shows (whole plant, leaf, flower, fruit, bark, fall color), its credit, and its license.
A palette layout asks for "the primary flower photo" and gets the right file for each plant.
firm_saved_plant, project, project_plantThe Save feature. One table holds the firm master list, and each project has its own saved list.
Saving is just adding a row. Removing a plant from one project doesn't touch the others or the main plant list.
region + plant_native_regionWhere a plant is native, at several levels: nation, multi-state, state, ecoregion, local. Each link says native or introduced, and the source.
The spreadsheet's Yes/No is kept as entered, since it doesn't say native to where.
vendorAn empty placeholder for a later phase.
So suppliers can connect to plants later.
